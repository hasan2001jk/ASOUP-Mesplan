# Mesplan (:8687) — анализ и план

Служба заявок МЕСПЛАН (месячный план перевозок). Java 8, Gradle, Spring Boot,
SQL Server 2005 (`mesplan` на 198.1.2.246). Вызывает только фронт Oper, раздел
`/oper/mesplan`. Ветка `dev`.

## 1. Как было (обзор 16.10.2026)

- **Служба на проде не работала.** Порт 8687 на .246 закрыт (подтвердил пользователь).
  Из исходника она и не могла запуститься: `server.ssl.enabled=true` без хранилища
  ключей → «Could not load key store 'null'».
- **С рабочей базой код не сходился.** Схема восстановлена из кэша IntelliJ
  (`docs/schema-2025-01-22.sql`). В `orders` нет колонки `header`, а «государство
  назначения» лежит в колонке `strbazn`; сущность ждала `header` и `strnazn`. Любое
  чтение и запись заявки давали бы «Invalid column name».
- **Строки администраций не сохранялись бы никогда:** `orderdetails.orderid` был
  отмечен `insertable=false` и на связи, и на поле — колонку не писал никто.
- **Ответ загрузки — конверт `{message}` и на успех, и на ошибку** (как было
  у AsoupServer, §31 там): успех показывался красным, ошибка — цифрой «1»/«2».
- Разбор файла резал строку вручную: неверный файл → «2» без пояснения; перевод
  строки в конце файла валил разбор; «Причина отказа» последней администрации
  без завершающего «^» терялась.
- Фронт: «Ввод» — заглушка с выключенной «Сохранить», одна строка администрации,
  в заявку не попадавшая; «Просмотр» — «в разработке».
- Общее со всеми службами: пароль `sa` в properties, нет проверки токена,
  `show-sql=true`, `TestController`, нет тестов.

Старая программа `docs/mesplan.exe` (Delphi, «mesplan2006», в git не кладётся) —
настольная, с таблицами dBase. Сервером не была; полезна как справка: таблицы
WORK/WORK1 совпадают с `orders`/`orderdetails`, в ней же были плановые сообщения
0304/0305/0306, которых в Java нет (см. §4).

## 2а. 19.10.2026 — действующая схема, архив сообщений, ответный файл

**Схема.** Выгрузка из SSMS показала, что база изменилась после снимка IntelliJ:
`header varchar(50)`, `strnazn` (не `strbazn`), `ftype varchar(4)`. Сущность
возвращена к ним (`db81c58`); действующая схема — `docs/schema.sql`, стенд по ней.

**Архив** (`docs/mesplan_messages`, 189 МБ, в git не кладётся): входящая почта
МЕСПЛАН 2018–2026 и исходники старой программы `Prog/mesplan2016` (Delphi:
`main.pas` — разбор, `order.pas` — ответный файл).

| Файлы | Что это |
|---|---|
| `PL_K…` (93 010), `PLAN…` (381), `PL_E…` (31) | входящие планы: по заявке на строку, администрации 27 → 29 → 66 |
| `RCPL_K…`, `RCPLAN…` | квитанции на НАШИ ответы: «обработано N» или ошибки («Неизвестный вид строки», «Запись по данной заявке не найдена») |
| `RYPL_K…`, `ROPLOK…` | ответы других администраций |
| `Prog/mesplan2016/2017–2019/*.txt` (11 131) | ответы, записанные старой программой |

Что из этого следует и сделано (`30aaa3b`, фронт `ef72589`):

- **В файле много заявок** (у 20 % файлов больше одной, у PLAN — сотни). Разбор и
  загрузка — все строки одной транзакцией; повторная загрузка файла — 409.
- **Ответный файл** (`GET /api/order/answer?header=`), как «Ok» в `order.pas`:
  идентификатор — как кнопка «Сформировать» (`PL_K` + `66` + месяц +
  `-ГГГГ-ММ-ДД-чч.мм.сс.мс123`, до 31 знака нулями, `_NV_2013.1`; время −1 ч),
  затем строки заявок, CP866, CRLF. Строки берутся **из исходного файла**
  (хранится при загрузке, `mesplan.files.dir`) и меняются только в полях,
  изменённых в базе: числа у нас в числовых колонках, ведущие нули иначе терялись бы.
- **Проверено на всём архиве** (`ArchiveRoundTripTest`, `-Dmesplan.archive=…`):
  93 382 из 93 422 файлов разобраны (40 битых — пустые, квитанция под именем PL_K,
  обрывки; отказ с номером строки); без правок 192 970 из 192 970 строк и 93 382
  файла выходят байт в байт; ответ администрации 66 — 190 555 из 190 555, меняются
  ровно результат и причина. На стенде в браузере — то же на настоящем файле.
- **Коды результата** (по причинам в архиве): 0 — не рассмотрена; 1 — согласована
  («При условии соблюдения СМГС…», «кроме вагонов с осевой нагрузкой 25 т»);
  2 — отказ («нет гарантийного письма», «нет разрешения ПФ»); 3 — отказ по тех.
  возможностям / изменена дата. В форме — списком.
- **Чем ответы старой программы отличаются от входящих** (17 711 сопоставленных
  строк): «Вид строки» `2 → 2s` (15 388), `3 → 2s` (1 055), `5/6 → 001` (231);
  результат 66 `0 → 1` (15 174). Плюс случайные искажения самой программы: обрезка
  хвостовых пробелов (dBase), нетто до 7 знаков, порча кавычек «╧…▌» при
  DOS↔Windows, в части строк — сдвиг полей. Наш ответ этих искажений не делает:
  всё, что оператор не менял, уходит как пришло.
